# We-Pixel

픽셀 아트를 **자동 생성 → 픽셀 단위 편집 → 유니티용 패키지로 내보내기** 하는 웹 도구입니다.

에디터는 웹 네이티브(React + Canvas)이고, 유니티는 결과물의 소비처입니다.
픽셀 격자를 칠하고 PNG를 뽑는 일에 Unity WebGL을 끼우면 5~15MB 빌드와 재빌드 대기가
붙는데, 정작 유니티가 필요한 부분은 export 포맷뿐이기 때문입니다.
현재 클라이언트 번들은 gzip 95KB입니다.

## 시작하기

```bash
npm install
npm run dev
```

`http://localhost:5173`

## 기능

**화면 구성** — 브라우저를 절반 폭으로 써도 캔버스가 화면 대부분을 차지합니다.

상주하는 것은 좌우 아이콘 레일 48px씩, 전부 합쳐 96px뿐입니다.
760px 창에서 캔버스가 87%를 차지합니다. 나머지는 전부 모달과 팝오버로 뺐습니다.

- *왼쪽 레일* — 도구 7개, 대칭·격자 토글, 되돌리기. 브러시와 색상은 팝오버.
  아이콘에 마우스를 올리면 설명이 **즉시** 뜹니다. 네이티브 `title` 속성은
  브라우저가 1초쯤 지연시키는데, 아이콘만 있는 UI에서는 그동안 무슨 버튼인지
  알 수 없어 직접 그립니다.
- *오른쪽 레일* — AI 생성, 자동 생성, 이미지 가져오기, 저장소, 내보내기,
  캔버스 크기. 각각 모달로 열립니다.
- 상단 바를 없애고 상태 표시를 캔버스 좌상단에 얹었습니다. 세로 공간을 캔버스에 줍니다.

**페이지** — 상단 탭으로 여러 그림을 동시에 열어 둡니다. 한쪽에서 복사해
다른 페이지에 붙여넣을 수 있습니다 — 클립보드는 페이지 밖에 있습니다.

내용은 브라우저에 자동 저장되어 새로고침해도 남습니다. 저장은 그릴 때마다가
아니라 잠잠해진 뒤 한 번만 합니다 — 큰 캔버스에서 버벅이기 때문입니다.
탭을 닫으면 저장된 내용도 사라집니다. 되돌리기는 페이지마다 따로 쌓입니다.

**선택 · 복사 · 이동** — 사각 선택 도구(S)로 영역을 잡고, 선택 안을 끌어 옮기거나
복사·잘라내기·붙여넣기 합니다. `Ctrl+C/X/V`, `Ctrl+A`(전체), `W`(그려진 부분만),
`Delete`(지우기), `Esc`(선택 해제).

옮기기는 잘라내기+붙여넣기와 같지만 한 함수로 둡니다 — 되돌리기 한 번으로
복구되어야 하기 때문입니다. 캔버스를 넘어간 부분은 잘립니다. 붙이려고 캔버스가
멋대로 커지면 유니티 스프라이트 크기가 어긋납니다.

**편집** — 펜, 지우개, 채우기, 직선, 사각형(외곽/칠), 스포이드.
브러시 크기 1~8, 좌우/상하 대칭 스탬프, undo/redo 64단계, 4~256px 캔버스.

확대율은 창 크기를 실측해 자동으로 맞춥니다(최대 64x). 직접 확대·축소하면
그때부터 자동 맞춤을 멈춥니다 — 창 크기가 바뀔 때마다 값이 튀면 작업에
방해가 되기 때문입니다.

측정은 `ResizeObserver`가 주 경로이고 `window.resize`가 보조입니다. 관측자
하나에만 의존하면 그것이 지연되거나 막힌 환경에서 캔버스가 스테이지를 넘칩니다.

**Ctrl(Cmd) + 휠**로 캔버스를 확대·축소합니다. 커서 아래의 픽셀이 제자리에
남도록 스크롤을 함께 보정하므로, 확대해도 보던 곳을 잃지 않습니다.
확대 폭은 현재 배율에 비례합니다 — 항상 1씩이면 40x에서 답답합니다.

React의 `onWheel`은 루트에 passive 리스너로 붙어 `preventDefault`가 무시됩니다.
그대로 두면 캔버스가 확대되면서 **브라우저 페이지 확대도 같이** 일어나므로,
네이티브 리스너를 `passive: false`로 직접 붙였습니다.

스크롤은 안쪽 `.stage-scroll`이 맡고 바깥 `.stage`는 오버레이 기준만 잡습니다.
`overflow: auto` 컨테이너 안의 `absolute` 요소는 내용과 함께 스크롤되므로,
실제 크기 미리보기를 그 안에 두면 확대해서 스크롤할 때 같이 흘러가 버립니다.

**커서 표시** — 마우스를 올린 칸을 캔버스에 테두리로 즉시 표시합니다.
브러시 크기와 좌우/상하 대칭이 그대로 반영되므로, 찍기 전에 어디가 칠해질지
보입니다. 어두운 선과 밝은 선을 겹쳐 그려 어떤 배경에서도 보이게 했습니다.

커서 표시와 좌표 읽기는 React 상태를 거치지 않습니다. `pointermove`마다
`setState`를 하면 레일과 미리보기까지 다시 그려집니다. 체커보드도 타일 패턴으로
한 번만 만들어 둡니다 — 칸마다 `fillRect`를 돌면 2048px 캔버스에서 6만 번이
넘고, 그 비용이 그대로 입력 지연이 됩니다.

**실제 크기 미리보기** — 우측 하단에 1x / 2x / 4x를 함께 띄웁니다.
캔버스는 4~256px 입니다. 자주 쓰는 크기는 버튼으로 있고(16 ~ 256),
그 사이 값은 직접 적을 수 있습니다.

확대해서 잘 그린 그림이 1배율에서 뭉개지는 것은 픽셀 아트에서 가장 흔한
함정이라, 실제 크기를 항상 같이 봐야 합니다. 스트로크 중에도 실시간으로
갱신됩니다 — React 상태를 거치지 않고 캔버스와 같은 경로로 그립니다.

**주사위 세트** — 컨셉 하나를 적으면("불꽃", "얼음", "뼈") 모델이 배색을 정하고
**열두 장**이 한 벌로 나옵니다: 세 면이 보이는 등축 여섯, 한 면만 보이는 정면 여섯.

형태는 그리지 않습니다. `frames/` 의 참고 주사위에서 뜬 것을 그대로 씁니다.
모델이 정하는 것은 색뿐이고, 응답 스키마에 `rows` 가 없어 형태를 돌려줄 방법
자체가 없습니다.

각 색이 무엇인지 메타데이터로 들고 있습니다. `a`, `b`, `c` 로만 두면 몸통과
눈을 따로 바꿀 수 없습니다 — 색조 하나로 전부 밀면 붉은 눈이 파란 눈이 되어
"돌 몸통에 붉은 눈" 같은 조합을 만들 수 없습니다.

| 자리 | 무엇 |
| --- | --- |
| `outline` | 실루엣 외곽선 |
| `edge` | 밝은 모서리 (면과 면 사이) |
| `faceLit` | 윗면과 왼쪽면 |
| `faceEdge` | 오른쪽면 모서리 |
| `faceShade` | 오른쪽면 (그늘) |
| `pipEdge` | 눈이 파인 자국 |
| `pipShade` / `pipLit` | 눈의 어두운 쪽 / 밝은 쪽 |

역할은 굽는 단계에서 **그림을 보고** 정합니다. 문자를 박아 두면 참고 그림을
바꿨을 때 조용히 어긋납니다. 눈은 채도로, 외곽선은 투명과 맞닿은 비율로,
나머지는 어느 면에 쓰이는지로 가릅니다.

몸통과 눈은 따로 계산합니다. 함께 넣으면 대표 색조가 하나로 잡혀 붉은 눈이
몸통을 따라 끌려갑니다.

채도는 배율만으로 부족합니다 — 0에 무엇을 곱해도 0이라, 무채색 돌 몸통은
아무리 곱해도 회색입니다. 그래서 더하는 값을 따로 둡니다.

모델에게도 문자가 아니라 이 이름을 줍니다. "눈의 밝은 쪽"이라는 것을 알고
고르는 쪽이 훨씬 낫습니다.

두 가족이 배색 하나를 **문자까지** 함께 씁니다. 참고 그림에서 팔레트가 8/9
겹쳤고, 어긋난 하나는 채널차가 2뿐이라 굽는 단계에서 합쳤습니다 — 손으로 그린
그림에는 채널 하나가 어긋난 색이 섞이고, 그대로 두면 공용 팔레트에서 서로 다른
자리를 차지해 배색 하나를 열두 장에 못 입힙니다. 기준은 **등축** 쪽입니다. 매핑을 장마다 다시 만들면 같은
회색이 장마다 다른 색이 되어 따로 만든 주사위처럼 보입니다. 결과를 `toSpec` 으로
다시 매기는 것도 안 됩니다 — 장마다 색의 등장 순서가 달라 같은 회색이 다른
문자가 되고, 그러면 배색 하나를 여섯 장에 다시 입힐 수 없습니다.

AI 없이 색조 슬라이더만으로도 세트가 나옵니다. 형태는 어느 쪽이든 같습니다.

**유니티 시트** 버튼은 여섯 장을 한 텍스처(384x64)로 묶고 `.meta` 에 칸 정보를
넣습니다. Sprite Editor 를 열 필요가 없습니다. 따로 내보내면 면을 바꿀 때마다
다른 스프라이트를 참조해야 해서 굴리는 연출을 짜기 번거롭습니다 — 시트 한 장이면
인덱스만 바꾸면 됩니다.

유니티의 `rect` 는 텍스처 **아래**에서 잽니다. 화면 좌표를 그대로 넣으면 위아래가
뒤집힌 채 잘립니다.

스프라이트 id 는 이름에서 뽑습니다. 0으로 두면 유니티가 임포트할 때 새로 매기고,
그러면 이미 씬에 놓인 참조가 끊깁니다. 다시 내보내도 같은 id 가 나와야 합니다.

AssetPostprocessor 는 시트를 건드리지 않습니다. `spriteImportMode` 를 무조건
`Single` 로 되돌리면 `.meta` 의 칸 정보가 지워져 여섯 칸이 한 장으로 합쳐집니다.

**아이템 칸** — 참고 칸 하나에서 등급 여섯을 만듭니다.

| 등급 | | 색 |
| --- | --- | --- |
| Common | 일반 | 흰색 |
| Uncommon | 고급 | 녹색 |
| Rare | 희귀 | 파란색 |
| Epic | 영웅 | 보라색 |
| Legendary | 전설 | 노란색 |
| Mythic | 신화 | 빨간색 |

참고 그림이 **전설(금색)** 이라 나머지 다섯은 색조만 옮겨 만듭니다. 형태가 한
픽셀도 다르지 않으므로 여섯 칸이 나란히 놓여도 어긋나지 않습니다. 전설을 다시
만들면 원본과 정확히 같은 색이 나옵니다 — 테스트가 그것을 확인합니다.

색조 기준은 **테두리** 입니다. 매핑은 대표 색조를 목표에 맞추는데, 이 그림의
대표 색조는 넓이가 큰 어두운 갈색 단들에 끌려 테두리보다 20도쯤 낮습니다.
보정하지 않으면 "초록으로" 라고 했을 때 테두리가 청록으로 나옵니다.

속은 세로 일곱 단의 그라데이션입니다. 위에서 아래로 밝아지는 순서가 이 그림의
입체감이고, 흐트러지면 평평한 사각형이 됩니다. 등급마다 그 순서가 지켜지는지
테스트가 봅니다.

**UI 키트** — 컨셉 하나로 주사위·버튼·패널을 한 벌로 만듭니다.

따로 뽑으면 색이 안 맞습니다. 같은 컨셉으로 두 번 물어보면 모델이 매번 다르게
답하기 때문입니다. 한 번에 다 받아야 한 벌이 됩니다.

자리 이름 앞에 무엇의 자리인지 붙입니다 (`dice.*`, `ui.*`). `outline` 은 양쪽에
다 있는데 굵기도 쓰임도 달라 같은 색이어야 할 이유가 없습니다 — 접두어가 없으면
하나가 다른 하나를 덮습니다.

AI 없이 톤 슬라이더만으로도 한 벌이 나옵니다. 주사위 눈만은 몸통 반대쪽 색조로
둡니다 — 몸통을 따라가면 몇 개인지 안 읽힙니다.

내보내면 텍스처가 **세 장**으로 나뉩니다. 크기가 다른 것을 한 텍스처에 섞으면
칸이 가장 큰 것에 맞춰지고, 9-슬라이스 테두리는 칸 가장자리를 기준으로 하므로
작은 그림의 테두리가 엉뚱한 자리를 가리킵니다.

**버튼** — 참고 버튼 한 장에서 어떤 크기든 만듭니다.

받은 것은 32/64/96 세 장이었지만 하나만 씁니다. **9-슬라이스**라 가장자리를
그대로 두고 가운데만 늘리면 나머지 둘이 한 글자도 안 틀리고 재현됩니다.
`buttonSpec` 이 만든 것과 원본 PNG 가 같은지 테스트가 확인합니다.

캡은 사방 5px 입니다. 늘어나는 가운데를 찾는 규칙은 "그 구간의 모든 줄이 서로
같다" 입니다 — 한 줄만 복사해도 같은 그림이 나온다는 뜻입니다. 캡은 작을수록
좋습니다. 크게 잡으면 늘릴 수 있는 폭이 좁아지고 작은 버튼에서 캡끼리 겹칩니다.

역할은 다섯입니다: `halo`(바깥 흰 테두리) `outline` `bevelLit`(왼쪽 위 경사)
`face` `bevelShade`(오른쪽 아래 경사).

상태는 넷이고 **형태는 어느 상태에서도 같습니다.** 크기가 달라지면 눌렀을 때
옆 요소가 밀립니다.

- *눌림* 은 경사를 뒤집습니다. 빛을 받던 쪽이 그늘이 되면 같은 그림이 파인 것처럼
  보입니다 — 픽셀 아트 버튼이 오래 쓰는 방법입니다.
- *올림* 은 밝게, *꺼짐* 은 색을 빼서. 외곽선만은 어느 상태에서도 그대로입니다.
  검정이 회색으로 뜨면 픽셀 아트가 흐릿해 보입니다.

**컨셉으로** 버튼을 칠할 수도 있습니다. "나무", "돌", "유리" 처럼 적으면 모델이
다섯 자리에 색을 정합니다. 주사위와 같은 방식이고 응답 스키마에 `rows` 가 없어
형태를 돌려줄 방법 자체가 없습니다. 밝기 순서(`halo > bevelLit > face >
bevelShade > outline`)를 지키라고 명시합니다 — 깨지면 버튼이 눌린 것처럼, 또는
납작한 사각형으로 보입니다.

세로로도 늘어나므로 **같은 한 장이 버튼도 되고 패널도, 창틀도** 됩니다.
자주 쓰는 크기는 버튼으로 넣어 뒀습니다 (버튼 / 넓은 버튼 / 작은 칸 / 패널 / 창틀).

내보내면 `.meta` 에 `spriteBorder` 가 들어갑니다. 유니티에서 Image 를 Sliced 로
두면 **한 스프라이트가 모든 크기를 감당합니다.**

**색 변형** — 지금 캔버스에 있는 그림의 색만 바꿔 여러 벌을 한 번에 뽑습니다.
같은 주사위의 다른 색, 같은 갑옷의 다른 등급처럼 **이미 그린 것으로 세트를
만들 때** 씁니다.

형태를 만들어 내는 기능은 두지 않았습니다. 절차적으로 그린 그림은 사람이 그린
것과 같아질 수 없고, 색만 바꾸는 쪽은 형태가 유지된다는 것을 코드로 보장할 수
있습니다. 형태는 그리는 대신 받아 둡니다 — `frames/` 참조.

  팔레트 매핑으로만 처리하므로 픽셀의 자리와 알파는 한 바이트도 바뀌지
  않습니다. 형태가 유지된다는 것이 코드로 보장됩니다 — 부탁이 아니라.

  색조를 목표값으로 그냥 몰아넣으면 그림이 단색이 됩니다. 원본의 대표 색조에서
  각 색이 얼마나 벗어나 있었는지를 그대로 옮깁니다. 밝은 면은 따뜻하고 그늘은
  차가운 픽셀 아트의 색 배치가 그 차이에 들어 있습니다.

  **가상 생성** 버튼은 색조를 손으로 돌리는 대신 어떤 느낌인지만 적으면
  ("불꽃", "얼음", "황금") 어울리는 배색을 모델이 정해 여러 벌로 돌려줍니다.
  모델에게는 형태를 돌려줄 방법 자체가 없습니다 — 응답 스키마에 `rows`가
  없습니다. 그림을 그리게 하면 "색만 바꿔줘"라고 해도 형태가 같이 바뀝니다.

  형태는 반복을 접은 표기(`a~10` = a가 10칸)로 보냅니다. 토큰이 60% 줄고,
  모델이 글자를 셀 일이 없어집니다 — LLM은 같은 글자를 28번 적으라고 하면
  27번이나 29번을 적습니다. 개수를 숫자로 적게 하면 셀 일이 없고, 펼칠 때
  합이 `w`와 맞는지 확인하므로 틀린 줄이 조용히 지나가지 않습니다.

  대표 색조는 원형 평균으로 구합니다. 색조는 각도라 350°와 10°의 산술 평균은
  180°, 즉 정반대 색이 나옵니다. 무채색은 빼고 셉니다 — 외곽선 검정이 픽셀
  수로는 가장 많은 경우가 흔한데, 그 색조는 0°(빨강)로 잡혀 대표색을 통째로
  끌어당깁니다.

**AI** — 네 가지 모드가 있고, 자주 쓰는 요청은 버튼으로 제공합니다.

| 모드 | 하는 일 | 원본 보존 |
| --- | --- | --- |
| 새로 그리기 | 프롬프트로 생성 | 덮어씀 |
| **색만 바꾸기** | 색 배합만 교체 | **모양 100% 고정** |
| **덧붙이기** | 요소 추가 (원본 위 / 뒤 선택) | 위: 가린 부분만 · 뒤: **100% 고정** |
| 고치기 | 그림 전체를 수정 | 지시로 부탁 |
| **가상 생성** | 배색 여러 벌을 한 번에 (색 변형) | **모양 100% 고정** |
| **주사위 세트** | 컨셉 하나 -> 주사위 열두 장 | **구운 프레임 그대로** |
| **버튼 컨셉** | 컨셉 하나 -> 버튼 네 상태 | **구운 프레임 그대로** |
| **UI 키트** | 컨셉 하나 -> 주사위 + 버튼 + 패널 | **구운 프레임 그대로** |

덧붙이기는 위치를 고릅니다. **원본 뒤**는 빈 자리에만 넣어 원본을 한 픽셀도
건드리지 않지만, 모자가 머리를 덮을 수 없어 뒤에 끼워진 것처럼 보입니다.
**원본 위**는 새 요소가 원본을 가릴 수 있습니다 — 모델이 투명으로 둔 자리는
원본이 그대로 남으므로 통째로 다시 그리는 것과는 다릅니다. 원본을 60% 넘게
덮으려 하면 덧붙이기가 아니라 다시 그린 것으로 보아 막고 알립니다.

**색만 바꾸기는 모델에게 그림을 그리게 하지 않습니다.** 색 목록만 받아 기존
픽셀에 적용합니다. 그리드를 요청하면 "색만 바꿔줘"라고 해도 형태가 같이
바뀝니다 — 주사위 눈 모양이 달라지는 식입니다. 실측에서 형태가 한 픽셀도
바뀌지 않은 채 파랑 4색이 빨강 5색으로 바뀌었습니다.

모델이 빠뜨린 색은 원래 값을 지킵니다. 검정이나 투명으로 채우면 그림이
망가집니다.

**덧붙이기가 핵심입니다.** 지시만으로는 모델이 전체를 다시 그리는 것을 막을 수
없습니다. 서버가 원본이 불투명한 자리를 아예 덮어쓰지 못하게 병합하므로,
모델이 무엇을 보내든 기존 그림은 한 픽셀도 바뀌지 않습니다. 실측에서
"모자를 씌워줘"에 원본 272px 전부 유지, 훼손 0px, 새로 49px 추가였습니다.

고치기는 요청과 무관한 부분을 유지하도록 지시하고 temperature를 낮춥니다 —
실측에서 실루엣이 100% 유지된 채 파랑 4색이 빨강 4색으로 바뀌었지만, 이쪽은
보장이 아니라 경향입니다.

보낼 때도 그림을 줄입니다. 256px 그리드를 그대로 보내면 65,536자라 모델이
읽지도 못합니다. 색이 많으면(사진 등) 보낼 사본만 양자화하며, 캔버스는
건드리지 않습니다.

경로는 두 가지입니다.

- *MCP*: Claude Code에서 대화로 지시합니다. API 키가 필요 없습니다.
- *Gemini*: 웹 UI에 프롬프트를 입력합니다. `.env`에 키가 필요합니다.

**이미지 가져오기** — 사진이나 일러스트를 픽셀 아트로 변환합니다.
캔버스에 직접 끌어다 놓거나 패널에서 고릅니다.

**새 캔버스로 대체하거나, 현재 그림 위/뒤에 붙일 수 있습니다.** 붙일 때는
9방향 위치를 고르고, 캔버스 크기는 유지되며 넘치는 부분은 잘립니다 —
넣으려고 캔버스가 멋대로 커지면 유니티 스프라이트 크기가 어긋납니다.
합성은 선택 붙여넣기·AI 덧붙이기와 같은 `core/compose.ts`를 씁니다.

단순히 파일을 여는 것이 아니라 **축소 + 색상 양자화**입니다. 1920x1080 사진을
그대로 넣으면 색이 수만 종이라 픽셀 아트로 보이지도 않고 spec 포맷
(팔레트 문자 75개)에도 담기지 않습니다. 축소를 먼저 하고 색을 줄입니다 —
반대로 하면 느린 데다 축소하며 중간색이 다시 생겨 팔레트가 어긋납니다.

- *area* : 원본 영역을 평균냅니다. 사진·일러스트용 기본값.
- *nearest* : 이미 픽셀 아트인 이미지가 확대 저장된 경우(16x16을 8배로 키운
  128x128 등) 평균을 내면 도트가 뭉개지므로 이쪽을 씁니다. 확대 배수를
  자동 감지해 안내합니다.

**확대 배수 감지는 색 경계의 정렬로 판정합니다.** 예전에는 연속 구간 길이의
최대공약수를 썼는데, 1픽셀짜리 디테일이 하나만 있어도 결과가 1이 되었습니다.
주사위처럼 몸통은 굵은 블록인데 눈만 잘게 찍힌 그림에서는 항상 실패합니다.

부분마다 해상도가 다르면 격자를 벗어난 경계 수를 함께 알리고,
**격자에 맞추기**로 하나의 해상도로 통일할 수 있습니다. 블록마다 다수결 색으로
정리하므로 잘게 찍힌 디테일은 블록 색에 흡수됩니다.

색상은 미디언 컷으로 줄입니다. 알파는 이진화합니다 — 반투명 경계가 남으면
유니티에서 Point 필터와 겹쳐 지저분한 테두리가 생깁니다.

**색상 교체** — 캔버스에 이미 그려진 색을 다른 색으로 바꿉니다.
사용 중인 색이 세로 목록으로 깔리고, 각 행에서 바꿀 색을 지정해
**여러 색을 한 번에** 교체합니다. 미리보기는 상단에 고정되어 있어
목록을 훑는 동안에도 결과 조합이 계속 보입니다.

매핑을 순서대로 적용하면 안 됩니다. `A→B`와 `B→C`를 함께 지정한 경우,
순차 적용은 원래 `A`였던 픽셀까지 `C`로 만들어 버립니다. 사용자가 지정한 것은
"A는 B로, B는 C로"이지 "A는 C로"가 아닙니다. 판정은 항상 원본에서 읽고
결과에만 씁니다 — 덕분에 두 색을 서로 맞바꾸는 것도 됩니다.

투명 처리가 핵심입니다. 투명 픽셀의 RGB는 대개 `0,0,0`이라 비교에 넣으면
검정과 구분되지 않으므로, 대상이 투명이면 알파만 봅니다. 결과를 투명으로
지정하면 해당 색을 지우는 동작이 됩니다.

허용 오차는 0이 기본입니다. 픽셀 아트는 색이 정확히 일치하는 것이 정상이고,
느슨하게 잡으면 명암 단계까지 함께 먹습니다. 사진에서 가져온 그림에만 올리세요.

**내보내기** — 유니티 폴더 구조를 그대로 담은 ZIP입니다.
압축을 풀고 `Assets`를 프로젝트 루트에 덮어쓰면 끝납니다.

```
Assets/WePixel/<Name>.png              스프라이트 (1배율 원본)
Assets/WePixel/<Name>.png.meta         임포트 설정 (Point, 무압축, 밉맵 없음)
Assets/WePixel/<Class>.cs              액터 스크립트
Assets/Editor/PixelArtImportSettings.cs  임포트 설정 강제 (에디터 전용)
<Name>.spec.json                       재편집용 원본 데이터
preview/<Name>@8x.png                  공유용 확대본 (유니티에 넣지 말 것)
README.md
```

## AI 생성

두 경로가 같은 spec 포맷을 공유합니다. 어느 쪽으로 만들어도 결과는 동일한 파일입니다.

### 경로 1 — MCP (권장)

Claude Code 같은 MCP 클라이언트가 이 프로젝트의 도구를 직접 씁니다.
**API 키도, 서버 배포도, 요청당 과금도 없습니다.**

```bash
npm run mcp:build
```

`.mcp.json`이 이미 있으므로 Claude Code를 이 폴더에서 열면 붙습니다.

| 도구 | 하는 일 |
| --- | --- |
| `draw_design` | 팔레트 + 행 문자열로 픽셀을 직접 작성 |
| `patch_rows` | 일부 행만 교체 (전체를 다시 안 보냄) |
| `generate_variants` | 저장된 디자인의 색만 바꿔 여러 벌 생성 |
| `generate_dice_set` | 주사위 열두 장(등축 6 + 정면 6)을 한 벌로 생성 |
| `generate_button` | 9-슬라이스 버튼 네 상태 생성 (크기 자유) |
| `get_design` | 저장된 디자인을 이미지 + 행 데이터로 조회 |
| `list_designs` | 작업 폴더 목록 |
| `export_unity_package` | 유니티 ZIP을 `workspace/exports/`에 기록 |

핵심은 **모든 생성/조회 도구가 렌더된 PNG를 함께 반환**한다는 점입니다.
모델이 자기 결과를 보고 고칠 수 있어야 형태가 제대로 나옵니다.
좌표만 다루면 그림이 무너집니다.

`draw_design`과 `patch_rows`는 호출자가 쓴 팔레트 문자를 그대로 저장합니다.
`toSpec`으로 재도출하면 문자가 등장 순서대로 재배정되어, 뒤이은 `patch_rows`가
자기가 쓴 `k`/`r`를 찾지 못합니다.

### LLM 배관

`server/llm.ts`가 Vercel AI SDK(`ai` + `@ai-sdk/google`)로 호출을 감쌉니다.
스키마는 zod로 정의하며, MCP 서버가 이미 쓰던 것과 같은 zod를 공유합니다.
직접 쓰던 fetch/파싱/에러 처리 136줄이 사라지고, 프로바이더 교체는 이 파일
한 곳만 고치면 됩니다 — `gemini-2.5-flash`가 단종됐을 때 호출 코드를 뒤져야
했던 일을 피합니다.

**다만 SDK도 "각 행이 정확히 w글자"는 강제하지 못합니다.** JSON 모양만
보장합니다. 그래서 행 길이·개수를 직접 검증하고, 어긋나면 **무엇이 틀렸는지
알려주고 한 번 더 묻습니다.** 실측에서 형식 오류 19건이 재요청 후 3건으로
줄었습니다. 재요청이 더 나빠지면 첫 응답을 씁니다.

토큰 단위로 형식을 강제하는 방법(outlines, xgrammar 같은 문법 제약 디코딩)은
Gemini HTTP API로 접근할 수 없습니다.

### 경로 2 — Gemini 프록시

웹 UI에서 프롬프트를 입력하는 방식입니다.

키를 주는 방법은 둘 중 아무거나 됩니다.

```bash
# A. 셸 환경변수 — 파일을 만들지 않음
GEMINI_API_KEY=여기에_키 npm run dev
```

```bash
# B. .env 파일 — 매번 입력하지 않음
cp .env.example .env
# .env 에 GEMINI_API_KEY 를 채운 뒤 개발 서버 재시작
```

모델은 `GEMINI_MODEL` 환경변수로 바꿀 수 있습니다. 기본값은 `gemini-3.6-flash`
입니다 — `gemini-2.5-flash`는 신규 사용자에게 더 이상 제공되지 않습니다.

키는 서버 프로세스에서만 읽히며 **클라이언트 번들에 들어가지 않습니다**.
브라우저에서 직접 호출하면 개발자 도구로 키가 그대로 노출됩니다.
인증은 쿼리스트링이 아니라 `x-goog-api-key` 헤더로 보냅니다. URL은 로그에 남습니다.

**모델에게 큰 그리드를 직접 시키지 않습니다.** 64px만 되어도 행마다 64글자를
세어야 해서 길이를 자주 틀립니다. 실측에서 64x64는 23개 행이 어긋났고 형태가
세 조각으로 갈라졌습니다. 32px 이하로 그리게 하고 정수배로 키웁니다 —
같은 프롬프트가 덩어리 3개에서 1개(본체 100%)로 바뀌었습니다.
이 덕분에 256px까지 지원합니다.

확대는 spec 상태에서 문자를 복제하는 방식입니다. 문서로 바꿔 리샘플하지 않으므로
색이 늘지 않고 팔레트 한도(75색)에도 걸리지 않습니다.

행 길이 보정은 **양쪽에서 고르게** 합니다. 끝에서만 자르거나 채우면 그림이
한쪽으로 밀려 좌우 대칭이 깨집니다.

Gemini의 `responseSchema`는 동적 키를 표현할 수 없어 팔레트를 배열로 받아
서버에서 레코드로 바꿉니다. 그리고 모델이 행 길이를 틀리는 것은 예외가 아니라
일상이므로, 길이·행 수·미정의 문자를 보정한 뒤 **무엇을 고쳤는지 UI에 알립니다**.
조용히 고치면 품질 저하의 원인을 찾을 수 없게 됩니다.

### 배포

API 핸들러는 Vite를 import하지 않으므로 개발 서버와 배포 서버가 같은 코드를 씁니다.
`server/api.ts`의 `createApiRouter`가 라우팅을 한 곳에 모아 두는 지점입니다.

```bash
npm run build
GEMINI_API_KEY=여기에_키 npm start     # 기본 4173, PORT 로 변경
```

`npm start`는 `dist/`를 서비스하면서 같은 API를 붙입니다. Node가 도는 곳이면
(VPS, Render, Railway, Fly 등) 그대로 올라갑니다.

#### Vercel

`api/generate.ts`가 `server/gemini.ts`의 핸들러를 그대로 얹은 서버리스 함수입니다.
개발 서버, `npm start`, Vercel 함수가 전부 같은 핸들러를 공유합니다.

```bash
npx vercel login      # 브라우저 인증 (한 번만)
npm run deploy        # = vercel --prod
```

`vercel`을 devDependency로 넣지 않았습니다(~50MB). `npx`로 그때만 받아 씁니다.
배포 후 Vercel 대시보드 > Settings > Environment Variables 에 `GEMINI_API_KEY`를
넣고 재배포해야 AI 생성이 켜집니다.

GitHub 저장소를 Vercel 대시보드에서 연결하면 push마다 자동 배포됩니다.
CLI 없이 쓰려면 이쪽이 편합니다.

**정적 호스팅만 쓰면 AI 생성이 동작하지 않습니다.** GitHub Pages, S3 등에
`dist/`만 올리면 `/api/generate`가 없어 404입니다. 이 경우 이 서버를 따로 띄우거나
`createApiRouter`를 서버리스 함수로 감싸야 합니다. 에디터와 알고리즘 생성,
export는 정적 호스팅에서도 전부 동작합니다.

#### 저장소는 환경에 따라 갈립니다

`src/storage/specStore.ts`가 시작할 때 `/api/designs`를 한 번 찔러보고 고릅니다.

| 환경 | 저장소 | MCP 순환 |
| --- | --- | --- |
| `npm run dev`, `npm start` | 서버 (`workspace/`) | 동작 |
| 서버리스 배포 (Vercel) | 브라우저 localStorage | 불가 |

서버리스의 파일시스템은 권한 설정으로 열 수 있는 것이 아닙니다. `/tmp` 외에는
읽기 전용이고, `/tmp`조차 인스턴스마다 따로이며 재활용되면 사라집니다.
그리고 권한과 별개로 **위치 문제**가 남습니다 — MCP 서버는 사용자 PC에서
로컬 파일을 읽으므로, 원격 서버가 그 디스크를 볼 방법이 없습니다.

배포판에서는 브라우저에 저장하고, 작업물을 챙겨 나갈 때는 `파일로 내보내기`로
`.spec.json`을 내려받습니다. `파일 열기`로 어느 환경에서든 다시 불러옵니다.

`npm run preview`에도 API가 붙어 있어 배포 전에 프로덕션 번들로 확인할 수 있습니다.

## 설계 메모

### 픽셀 데이터 포맷

팔레트 + 인덱스 그리드를 씁니다.

```json
{
  "w": 32, "h": 32,
  "palette": { ".": "transparent", "a": "#4080bf", "b": "#0e1a25" },
  "rows": ["........aaaa........", "......aabbbbaa......"]
}
```

32×32를 `colorsHex: [...]` 1024개 배열로 표현하면 LLM이 중간에 형태를 놓칩니다.
행 단위 문자열은 토큰이 1/10 수준이고 모델이 그림을 보면서 생성할 수 있어서,
이 포맷을 AI 생성 단계의 계약으로 씁니다.

### 내부 표현

문서는 `Uint8ClampedArray` RGBA 바이트 배열입니다.
`Uint32Array`를 쓰면 채널 순서가 엔디언에 의존하므로 의도적으로 피했습니다.

### 성능

- 오프스크린 버퍼는 문서마다 재사용합니다. 프레임마다 캔버스나 `Sprite`를
  새로 만드는 것이 이 종류 코드에서 가장 흔한 실수입니다.
- 스트로크 중에는 React 상태를 거치지 않고 직접 그립니다.
  `pointermove`마다 `setState`를 하면 렌더 왕복이 입력 지연으로 체감됩니다.
- 확대는 `imageSmoothingEnabled = false`. 픽셀 아트에서 보간은 금물입니다.

### 유니티 임포트

`.meta`는 유니티 버전마다 `serializedVersion`이 달라 100% 보장이 어렵습니다.
그래서 `AssetPostprocessor`를 함께 내보내 임포트 시점에 설정을 다시 강제합니다.
이쪽이 실질적인 안전망입니다.

생성되는 C#은 레거시 Input Manager를 씁니다. Player Settings의
Active Input Handling이 `Input System Package (New)` 단독이면 `Both`로 바꿔야 합니다.

점프를 켜면 `Rigidbody2D` 기반으로 전환됩니다. `transform.Translate`와
`Rigidbody2D`를 섞으면 물리 엔진과 싸우게 되기 때문입니다.
`Rigidbody2D.velocity`는 Unity 6에서 `linearVelocity`로 이름이 바뀌었으므로,
생성 코드는 `#if UNITY_6000_0_OR_NEWER`로 한 곳에서만 분기합니다.

npm test
